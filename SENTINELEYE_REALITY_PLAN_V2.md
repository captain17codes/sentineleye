## P0 — Legal and factual corrections (small, do first, ~1 hour)

### P0.1 Section 65B is no longer the law
The Indian Evidence Act, 1872 was replaced by the Bharatiya Sakshya Adhiniyam (BSA), 2023 from 1 July 2024. Section 65B is now **Section 63 BSA**.

- Search the whole repo (UI, PDF generator, `policy.ts`, FAQ, README, PROJECT_OVERVIEW, Demo Director notes, tests) for `65B`.
- Replace user-facing wording with: **"Section 63, Bharatiya Sakshya Adhiniyam, 2023 (formerly Section 65B, Indian Evidence Act, 1872)"**.
- In the PDF, replace the single footer line with a proper **Section 63(4) certificate block** in two parts:
  - **Part A (by the party / person in charge):** device and system description, statement that the system was operating properly, source of data (Sentinel scene IDs and acquisition timestamps), **SHA-256 hash values** of the evidence package (ledger block hash, scene hash), name/designation/signature/date placeholders.
  - **Part B (by an expert):** placeholder lines for the expert's name, qualification, statement of technical verification of the hash, signature/date.
- The PDF must show the hash of the evidence (ledger block hash + scene fingerprint). That is exactly what the new certificate asks for, so highlight it in the demo.
- Add a `legal.ts` constants file so the section name lives in one place.

### P0.2 Platform issues a draft, not a statutory notice
A software platform cannot itself issue a statutory eviction notice. Re-label across UI, PDF and docs:
- "Notice Issued" → **"Notice Drafted — Pending Officer Signature"** (internal state key may stay).
- PDF header: "DRAFT NOTICE FOR SIGNATURE BY COMPETENT AUTHORITY" with a signature block for the officer of the relevant authority (DDA / Forest Dept / Mines & Geology / L&DO).
- Add a final workflow state **"Signed & Served"** that an operator marks manually, which adds a ledger block.

### P0.3 Statutory table corrections (`backend/src/policy.ts` and the frontend policy constants)
- Delhi Development Act, 1957: cite **Section 29 (penalties), Section 30 (removal of unauthorised development), Section 31 (power to stop development), Section 31A (power to seal)**. Update the table text accordingly.
- The Forest (Conservation) Act, 1980 was renamed by the 2023 amendment to the **Van (Sanrakshan Evam Samvardhan) Adhiniyam, 1980**. Use "Forest (Conservation) Act, 1980 (now Van (Sanrakshan Evam Samvardhan) Adhiniyam, 1980)".
- Add a visible disclaimer on the Policy page: "Statutory references are indicative, for demonstration; verify against the current bare Act before any real enforcement."
- Add a one-line note on the Policy page that Delhi has special protective legislation on unauthorised development (the NCT of Delhi Laws (Special Provisions) Act, 2009, as extended from time to time) which can affect sealing/demolition; verify current status.

### P0.4 Satellite facts
- Sentinel-1B failed in 2021. Sentinel-1A operations ended on 29 June 2026. The current constellation is **Sentinel-1C + Sentinel-1D** with a **6-day** nominal revisit.
- Sentinel-2 nominal revisit is 5 days with two satellites at the equator (shorter at Delhi's latitude because of orbit overlap).
- Fix the Q5 answer in the viva guide, the Scan page text, FAQ and README: "Sentinel-2: 5-day nominal; Sentinel-1: 6-day (C+D)". Never write "combined 5-day".
- Resolution wording: Sentinel-2 10 m (visible/NIR). Sentinel-1 IW GRD is about 20 m × 22 m native resolution (ground range detected products are typically distributed at 10 m pixel spacing). Say "~10 m pixel spacing" and not "5×20 m".

## P1 — Real satellite data mode ("Replay with real Sentinel scenes")

Today every scene is generated by `scene.ts`. Keep it, but relabel it clearly as **"Calibration scenes (synthetic, ground truth known)"** and add a second source: **real data**.

### Data sources (all free)
- **Sentinel-2 L2A, optical:** Element 84 **Earth Search STAC API** (`https://earth-search.aws.element84.com/v1`, collection `sentinel-2-l2a`). Items expose Cloud-Optimized GeoTIFF assets (`red`, `nir`, `scl` scene classification) readable by HTTP range requests, so no backend is needed. Filter by bbox, date range and `eo:cloud_cover`.
- **Sentinel-1, SAR:**
  - Earth Search `sentinel-1-grd` is amplitude-only and not terrain corrected.
  - Microsoft **Planetary Computer `sentinel-1-rtc`** (radiometrically terrain corrected, VV/VH) is better for the Aravalli terrain, but a Planetary Computer account / SAS token is required.
  - Therefore SAR is processed **offline** (see below), not in the browser.

### Architecture: precompute real crops, replay in the browser
1. Create `tools/fetch_real_scenes.py` (Python, runs on a developer machine, not in the app) that for each chosen zone AOI (small bbox, e.g. 2×2 km):
   - Queries STAC for a T0 scene and a T1 scene, same season to avoid false seasonal change, cloud cover < 10%.
   - Reads red, nir, scl windows; writes `red`, `nir`, `scl` as compact arrays.
   - Reads Sentinel-1 RTC VV (convert to dB) for the same dates (± a few days) with the same orbit direction if possible.
   - Writes `frontend/public/real/<zoneId>/{t0,t1}.json` (or small PNG/Float32 binary) plus `manifest.json` containing: scene IDs, acquisition datetimes, CRS, geotransform, bbox, source URLs, processing steps.
2. In the app, add a **Data source toggle** on the Scan page: `Calibration (synthetic)` | `Real Sentinel (replay)`. Real mode loads the precomputed arrays and runs the **same worker pipeline** (cloud mask from SCL instead of synthetic cloud, real NDVI, real dSAR).
3. Show the real scene IDs and acquisition dates in the UI, PDF and ledger genesis block. `H0` must hash the real raster bytes.
4. Optional bonus ("Live fetch"): in-browser STAC query + COG window read for Sentinel-2 using `geotiff.js`, for NDVI only, with automatic fallback to replay data when offline. Never let the live path be required for the demo.

### Choosing real test sites (critical for credibility)
- Pick **2–3 AOIs where real change is visible** between T0 and T1 on Esri/Google imagery (a quarry expansion, a new construction block or cleared tract on the Yamuna floodplain or Aravalli belt). Verify by eye before using them.
- Also pick **1 AOI with no real change** to demonstrate that the system does not hallucinate detections.
- Record these as labeled ground truth in `frontend/public/real/ground_truth.geojson` (hand-drawn polygons).
- Add Sentinel-2 SCL cloud/shadow masking and a quality gate that rejects scenes with high cloud cover.

### Honest detection limits (put on a Limitations panel)
- A Sentinel-2 pixel is 10 m (100 m²). Detections below roughly 5 pixels are filtered, so very small structures are not detectable.
- NDVI loss alone cannot tell crop harvest from clearing; SAR helps but is not a guarantee. Results are **candidates for human verification**, not proof of violation.

## P3 — Make the ledger genuinely tamper-evident

Right now anyone with browser dev tools can edit blocks and recompute every hash, so tamper-evidence is only as strong as the storage.

1. **Operator signatures:** generate an ECDSA P-256 key pair with WebCrypto per operator (private key stored non-extractable in IndexedDB). Sign each block hash; store `signature` and `publicKey` in the block. `verifyChain()` must verify signatures as well as hashes.
2. **External anchoring:** after each major block (or on demand), show a **"Chain head"** hash with a copy button and an "Anchor" action that records the head hash outside the system's control. For the demo: write the head hash into a public location (e.g. a GitHub gist/commit, or a tweet-like public note) and display "Anchored at <time> → <link>". Explain: anchoring makes retroactive rewriting detectable even if an attacker recomputes every hash.
3. **Tamper demo, two levels:**
   - Naive tamper (edit data only) → hash mismatch at block N.
   - Smart tamper (edit data and recompute all following hashes) → chain looks internally valid, but the **anchored head hash no longer matches** → red banner "Chain head differs from anchored head". This answers the obvious viva question.
4. Add a `Merkle`-style evidence manifest to each block: hashes of the T0 raster, T1 raster, NDVI, SAR and the polygon GeoJSON, so the PDF can print them under Part A of the Section 63 certificate.

- Report results honestly, including misses. A slide saying "recall X%, precision Y%, limitations Z" is far stronger than "AI detects everything".
