```
→ vectorize to polygons → cadastral overlap (turf) → classify + severity

```

## 3. Phase 2 — Real scan engine (the core of the demo)

Create `frontend/src/engine/scan/`:

| File | Responsibility |
| :--- | :--- |
| `scene.ts` | Deterministic synthetic scene generator per zone: a 256×256 grid with bands `Red`, `NIR`, `SAR_VV_dB` for T0 (baseline) and T1 (current). Geotransform maps pixel → lat/lng using the zone's bounding box. |
| `scenarios.ts` | Planted ground-truth events per zone (see list below). |
| `cloud.ts` | Generates a cloud mask (smooth noise thresholded to the chosen cloud-cover %). Optical bands are invalid under cloud. SAR is unaffected. |
| `ndvi.ts` | `NDVI = (NIR − Red) / (NIR + Red)`; `dNDVI = NDVI_T1 − NDVI_T0`. |
| `sar.ts` | `dSAR = SAR_T1 − SAR_T0` in dB, plus a simple speckle filter (3×3 median/mean). |
| `fusion.ts` | Per-pixel decision (see rules below), mode-dependent. |
| `vectorize.ts` | Connected-component labeling (4-connectivity flood fill), drop blobs under `MIN_AREA_M2`, trace outline (or convex hull via turf), convert to GeoJSON polygon with the geotransform. |
| `overlay.ts` | For each detected polygon: `turf.intersect` with the zone polygon, `overlap% = area(intersection)/area(detection)`, area in m² via `turf.area`. |
| `classify.ts` | Class, severity and statutory mapping. |
| `worker.ts` | Runs the whole pipeline off the main thread, posts progress per stage. |

**Planted scenarios (ground truth), so results are explainable and repeatable:**

1. **Concrete construction** — NDVI drops sharply, SAR **increases strongly** (double-bounce, e.g. +4 dB or more). → `Unauthorized Construction`.
2. **Illegal mining pit** — NDVI drops sharply, SAR changes moderately with high roughness. → `Illegal Mining`.
3. **Clear-cut forest** — NDVI drops sharply, SAR drops or changes slightly. → `Deforestation`.
4. **Seasonal farming patch (false positive)** — NDVI drops, SAR change is low. → **must be rejected** and shown in the "raw vs validated" counter.
5. **Cloud-covered encroachment** — a real construction event sitting under cloud. Optical mode misses it, SAR and Fused catch it. This makes the cloud-cover slider and the optical/SAR/fused selector actually matter.
6. **Noise blobs** — tiny speckle-like changes that vectorization must filter out by minimum area.

**Detection rules (keep thresholds in `config.ts`):**

- Optical mode: flag where `dNDVI < -0.25` and the pixel is not cloud-masked.
- SAR mode: flag where `|dSAR| > 3 dB`.
- Fused mode: flag where optical and SAR agree; where optical is cloud-masked, fall back to SAR; where optical says change but SAR is low, reject as seasonal vegetation.
- Confidence score = weighted combination of `|dNDVI|`, `|dSAR|` and agreement between sensors.

**Severity rules:**

- Critical: overlap > 85% with core zone, or deep excavation in a sanctuary.
- High: heavy concrete or active mining.
- Medium: fencing, road cutting, agricultural encroachment.
- Low: peripheral vegetation disturbance.
- Only create an alert if overlap > 35%.

**Scan page wiring (`pages/Scan`):**

- The existing sensor cards (Optical / SAR / Fused) and cloud slider pass real parameters into the worker.
- Show a **stage-by-stage progress panel**: Ingest → Cloud mask → NDVI → SAR → Fusion → Vectorize → Cadastral overlay → Classify → Ledger commit.
- After completion, render on `<canvas>`: NDVI-difference heatmap, SAR-difference heatmap, and the change mask with detected polygons outlined, with a toggle between layers.
- Show real counters: `raw detections`, `rejected (false positive)`, `validated`, `below overlap threshold`. These come from the pipeline, not from constants.
- Detected polygons become real alerts in the store and appear on the Map and in Alerts immediately.
- Running the same zone + seed + mode + cloud % twice gives the same result. Changing cloud % from 10 to 80 visibly changes what Optical mode finds.

**Acceptance (write as vitest tests):** NDVI math on known values; vectorize returns the expected number of polygons for a known mask; overlap % for a hand-built polygon pair matches the hand calculation; Optical misses the cloud-covered scenario while Fused catches it; seasonal farm patch is rejected.

## 4. Phase 3 — Real SHA-256 ledger with tamper test

Create `frontend/src/engine/ledger.ts` using `crypto.subtle.digest('SHA-256', …)`.

- Canonical serialization: stable key-sorted `JSON.stringify` so the same payload always hashes the same.
- Genesis block `H0 = SHA256(ingestTimestamp + sceneId + sceneRasterBytesHash)`.
- Each block: `{ index, type, timestamp, payload, operator, prevHash, hash }` with `hash = SHA256(index + prevHash + timestamp + canonical(payload) + operator)`.
- Block types: `SCENE_INGEST`, `DETECTION`, `VERIFIED`, `NOTICE_ISSUED`.
- `appendBlock()`, `verifyChain()` (returns `{ valid, firstInvalidIndex, reason }`), persisted with the store.

**Ledger page / panel (add if not present):**

- Visual chain of blocks showing index, type, short hash and prev-hash link.
- **"Verify chain"** button → recomputes everything and shows a green seal.
- **"Simulate tampering"** button (clearly labeled as a demo control) → silently modifies one stored block's payload (e.g. changes a coordinate). The next verify shows red: `Block #N invalid — expected <hash>, found <hash>`, and every following block is marked as broken. A **"Restore"** button repairs it.
- Overview KPI "Ledger chain" must reflect the live `verifyChain()` result, not a hardcoded "verified".

**Acceptance:** vitest — valid chain verifies; mutating any block field flips verification and reports the correct index; chain is stable across reload.
